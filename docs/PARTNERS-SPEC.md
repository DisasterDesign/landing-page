# מודל שותפים — מפרט

**סטטוס:** טיוטה לאישור אלעד · 28.7.2026
**מחליף:** דוח שותפים עם חלוקה קשיחה 50/50 + עמלת מוכר קשורה לתפקיד `SELLER`

---

## המטרה בשורה אחת

שתי רמות חשיפה — **בעלים** רואה הכל, **שותף** רואה רק את מה שהוא ייצר —
כאשר לכל שותף תנאי חלוקה משלו, וללא ידיעה הדדית על קיומם של שותפים אחרים.

---

## 1. השותפים ותנאיהם

| שותף | תפקיד היום | סוג חלוקה | תנאים |
|---|---|---|---|
| אלעד | ADMIN | — | בעלים. רואה הכל, כולל עסקאות פרטיות |
| רועי | ADMIN → שותף | `RECURRING_SHARE` | 50% מהרווח, על עסקאות שהוא ייצר להן חוזה |
| דגרון | SELLER → שותף | `FIRST_MONTH` | 100% מהחודש הראשון של כל עסקה שהוא סגר |
| אלבז | חדש | `FIRST_MONTH` | כנ״ל |
| דניאל | חדש | `FIRST_MONTH` | כנ״ל |

**שני טיפוסים בלבד.** כל דבר מעבר לזה הוא הנדסת יתר — התנאים כבר סוכמו
מול השותפים ואינם צפויים להשתנות. הוספת שותף חדש = שורה בטבלה.

## 2. מודל הנתונים

### מודל חדש: `Partner`

```prisma
model Partner {
  id            String            @id @default(cuid())
  userId        String            @unique   // המשתמש שמתחבר
  user          User              @relation(fields: [userId], references: [id])
  displayName   String
  splitType     PartnerSplitType             // RECURRING_SHARE | FIRST_MONTH
  splitPercent  Float                        // 50 עבור רועי, 100 עבור השאר
  isActive      Boolean           @default(true)
  startedAt     DateTime          @default(now())
  endedAt       DateTime?
  createdAt     DateTime          @default(now())
}

enum PartnerSplitType {
  RECURRING_SHARE   // אחוז מהרווח, כל חודש, כל עוד הלקוח משלם
  FIRST_MONTH       // אחוז מהחודש הראשון בלבד, חד־פעמי
}
```

### שדות שמתווספים ל-`Agreement`

```prisma
partnerId          String?   // מי ייצר את העסקה. null = אלעד (עסקה פרטית)
splitTypeAtSigning PartnerSplitType?   // ננעל ברגע החתימה
splitPercentAtSigning Float?           // ננעל ברגע החתימה
```

**למה ננעל:** אם תנאי שותף ישתנו בעתיד, עסקאות שנסגרו קודם חייבות
להמשיך להתחשבן לפי מה שסוכם אז. בלי זה כל שינוי תנאים משכתב היסטוריה
כספית. גם אם היום אין כוונה לשנות — העלות היא שני שדות, והחלופה היא
חישוב מחדש של העבר.

### `Client` — נגזר, לא כפול

`Client.partnerId` **לא** נשמר בנפרד. שיוך לקוח נגזר מההסכם שייצר אותו,
כי ההסכם הוא מקור האמת של מי סגר. שדה כפול = שני מקורות אמת שיסתרו.

חריג: `Client.partner` הקיים (`"fuzion"` / אחר) הוא שדה legacy שמסמן
לקוחות מלפני השותפות. הוא נשאר, ואינו קשור למודל החדש.

### עסקאות פרטיות

`Agreement.partnerId = null` פירושו: אלעד הביא לבד, אין חלוקה. אין צורך
בדגל `isPrivate` נפרד — היעדר שותף הוא ההגדרה.

### נתונים קיימים

- כל ההסכמים החתומים הקיימים → `partnerId` = רועי, `RECURRING_SHARE 50%`
- `SellerCommission` הקיים נשאר כפי שהוא — הוא כבר מחשב חודש ראשון
  ומשמש כמנוע ל-`FIRST_MONTH`. אין עמלות רשומות היום (0 שורות), אז אין
  מה להמיר.

## 3. כלל החשיפה

**הסינון קורה בשאילתה, לא בתצוגה.**

כל שאילתה שמחזירה נתונים עסקיים מקבלת את זהות הצופה ומחילה:

```ts
// שותף: רק מה שהוא ייצר
partnerId: viewer.partnerId

// בעלים: ללא מסנן
```

זה כולל **סיכומים ואגרגציות** — MRR, גרפים, מוני לידים, דוח חייבים.
מספר מסכם לא מסונן מסגיר את היקף העסק כולו גם כשכל שורה מוסתרת.

הדפוס כבר קיים באפליקציה: `sellerIntentWhere` ב-`src/lib/leads/projection.ts`
מסנן לידים לפי המוכר. זו ההרחבה שלו לכל שאר הישויות.

### אי־ידיעה הדדית

שותף לא רואה:
- רשימת שותפים, בורר שותפים, או מונה "N שותפים"
- שמות של שותפים אחרים בשום מקום — כולל היסטוריית שינויים והתראות
- כל אגרגט שאינו מסונן אליו

## 4. מימוש ההרשאות — בלי תפקיד חדש

**אין `Role.PARTNER`.** הוספת ערך ל-enum מחייבת נגיעה בכל מקום שבודק
`role === "SELLER"` — ובמיוחד `resolveEligibleSellerId`
(`src/lib/leads/assignment.ts:35`), שבלעדיו **לידים חדשים יפסיקו להתנתב
בשקט**. במקום זה, עמודה אחת על `User`:

```prisma
isOwner Boolean @default(false)   // אלעד בלבד
```

- **בעלים** = `isOwner: true`
- **שותף** = `role: SELLER` (רועי מודמה לשם, דגרון כבר שם)

השער האמיתי הוא `isOwner`, לא `role`. הרווח: 61 מסלולי הבעלים כבר חוסמים
`role !== "ADMIN"`, ו-56 מסלולי השותף כבר קיימים כמשטח `/api/seller/*`
עם סינון אמיתי.

`Client` מקבל `ownerId` (ממולא מ-`creditedSellerId` → `createdBy` → אלעד).
`Agreement` לא מקבל עמודה — הוא כבר נושא `creditedSellerId` ו-`createdBy`,
אבל **חסרים עליהם אינדקסים** וכל שאילתת שותף תסרוק טבלה.

## 6. מלכודות שחייבות להיות מטופלות לפני ההדמיה של רועי

1. **ה-JWT מחזיק את התפקיד 24 שעות.** ה-middleware רץ ב-edge ולא קורא
   DB. לכן סגירת מסלולי הבעלים חייבת לקדום את הורדת רועי — אחרת יש חלון
   של יממה שבו הטוקן הישן עדיין פותח הכל. אחרי ההדמיה: סיבוב
   `NEXTAUTH_SECRET` כדי לכפות התחברות מחדש.
2. **`assertActorCanMutateLead` דורש התאמה בין התפקיד השמור לנטען**
   (`src/lib/leads/authorization.ts:194`). ברגע שרועי SELLER, כל
   `/api/leads/[id]/*` יחזיר FORBIDDEN — ה-UI שלו חייב לעבור ל-`/seller`.
3. **`notifyAllAdmins` יהפוך לרשימה של אחד.** נכון פונקציונלית, אבל השם
   משקר — לשנות ל-`notifyOwner`.
4. **בריף המוכר מחפש מייל קשיח** (`src/app/api/seller/brief/route.ts:25`)
   עם נפילה ל-`role: "ADMIN"` — כלומר רועי מקבל היום בריפים של דגרון.
5. **`sellerLeadScope` חושף לידים לא־משויכים** לפי `eligibleSellerId`.
   היום יש מנתב יחיד, אז אין התנגשות. עם ארבעה שותפים, שניים שיהיו
   eligible לאותו ליד ילמדו זה על קיומו של זה.
6. **חסר משטח `/seller` מלא:** אין `/api/seller/clients`,
   `/api/seller/dashboard`, `/api/seller/tasks`. שותף בלי דשבורד משלו
   ינותב לדשבורד הגלובלי.

## 5. סדר מיגרציה

כל שלב הפיך בפני עצמו, ומאומת לפני הבא.

1. **מודל בלבד** — `Partner` + השדות ב-`Agreement`, בלי לשנות התנהגות.
   רועי נשאר ADMIN. אימות: האפליקציה מתנהגת בדיוק כמו קודם.
2. **מילוי נתונים** — כל ההסכמים הקיימים משויכים לרועי. אימות: דוח
   השותפים מציג את אותם מספרים כמו לפני.
3. **סינון בשאילתות** — הוספת הסקופינג בכל המסלולים, אבל רועי עדיין
   ADMIN ולכן לא מושפע. אימות: הרצה כשותף מדומה מחזירה רק את שלו.
4. **הורדת רועי לרמת שותף.** אימות: הוא רואה את שלו, ואף אגרגט אינו
   מסגיר את השאר.
5. **דגרון לשותף**, ואז אלבז ודניאל.

**הסדר הזה מכוון:** ההפרדה מוכחת על רועי — מי שכבר ראה הכל ממילא — לפני
ששותף חדש נכנס. דליפה מול אדם שהצטרף אתמול היא נזק מסוג אחר.
